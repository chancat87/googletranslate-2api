googletranslate-2api v2.12.3 变更报告

2026-09-22 生产验收 + Spec Kit 规范 + 终局审计

一份让你“看懂这次变更里发生的一切”的报告，底部附 10 题测验，通过才算签收。

一、上下文与直觉

项目是什么：一个把 Google Translate 上游封装成 OpenAI 兼容翻译 API 的网关，带 Web UI、多 Key 池、缓存/限流/熔断、可观测与多路径部署。

核心直觉：既然要“上生产”，就不能只追求接口长得像；必须让调用方一次跑通、让部署方升级不断、让新人按文档能复现。因此本轮不是加花活，而是把“看起来能跑”升级为“已实测能跑”，并把判断依据固化进规范与报告。

关键取舍：不接 Immersive Translate 扩展内置 Key（凭证滥用/易吊销/ToS 风险），改用“用户自有多 Key 池 + DEMO 无 Key 降级”；单机热更新用 nginx 蓝绿双副本 + `proxy_next_upstream` 而不是简单 `docker compose up -d`，因为后者会中断；根路径按 `Accept` 头分流，浏览器进 UI、API 客户端仍拿 JSON，兼容两拨用户。

五、风险与边界（诚实声明）

边界状态
真实 Google Key只存在于服务器 `.env`；仓库/镜像/文档均不包含明文，本报告不展示
K8s 生产部署配置已就绪，但需配置 `KUBE_CONFIG_*` 才能真正落集群（当前为单机蓝绿 Docker）
更高并发单 Key 有极限；多 Key 池已实现，真实 N×QPS 需准备 N 个可用 Key 复测
自动更新Watchtower 未默认开启，避免未经确认自动滚版本；需要时按文档启用
无法 100% 证明“无 bug”已用测试/压测/升级回滚尽量压缩风险，但任何系统都不能宣称绝对无 bug

二、这轮做了什么（时间线）

  • v2.9.x：恢复仓库历史 Key 到本地 `.env`；真实上游 E2E 20/20；拒绝接入第三方扩展 Key 并出具审计文档；Key 可用性自检 API + UI。
  • v2.10.x：无 Key DEMO 模式；根路径浏览器直达 Web UI；启动脚本自动建 `.env`/自动开浏览器。
  • v2.11.x：完整 GitHub Actions CI/CD（缓存、并发取消、pip-audit、Gitleaks/Trivy/SBOM、Slack 通知、staging/production 部署与回滚）。
  • v2.12.0：单机零中断热更新：蓝绿双副本 + nginx 重试 + `upgrade.sh` + 可选 Watchtower。
  • v2.12.1：修复蓝绿 compose 在 1 核服务器上的 `cpus` 兼容问题（`APP_CPUS`）。
  • v2.12.2：生产部署验收审计；本报告 + Spec Kit 规范 + `workflow_status.md` 需求追踪矩阵。
