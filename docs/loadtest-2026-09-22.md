# 真实并发压测基线报告 (2026-09-22, v1.5.1)

> 环境: Windows 11 / Python 3.10.9 / uvicorn 单 worker / 真实上游 Google translate-pa (有效 key, 来自历史 .env)
> 工具: `scripts/loadtest.py` (纯 asyncio + httpx, cache/upstream 两模式, 每请求唯一文本, 分位延迟/错误率/429 计数)
> 原始证据: `docs/loadtest/*.json`

## 一、结论 (TL;DR)

| 问题 | 答案 (真实实测) |
|---|---|
| 能不能并发调用? | **能**。并发 1→40 全部返回 200, 全程 0 错误、0 429 (cache 与 upstream 模式均验证) |
| 最高支持多少并发? | **正确性上限未测到** (conc=40 仍全 200); 性能拐点在 conc≈5-10 |
| 本地承载 (缓存命中) | 单 worker 吞吐 ~20-27 QPS, p50 36-810ms; 瓶颈是单 worker 事件循环 + 控制台日志固定开销 (~36ms/请求), **不是连接池** |
| 真实上游 (冷文本) | 默认连接池(15) ~5.5-6 QPS; 调参连接池(40) conc20+ ~10.3 QPS, 显式连接池参数有实测价值 |
| 429 阈值 | 温和压测 (conc≤40, 总数≤60) **未触发 429**; 更狠的持续高压可能触发 Google 配额 (重试/熔断/冷却已兜底) |

> 高压时偶见上游重试 (日志: "上游重试第 2/3 次, 退避 0.5-0.7s"), 重试+熔断兜底生效, 最终仍 200。

## 四、怎么高并发调用 (可操作)

1. **调大上游连接池** (v1.5.1 新增可配):
   ```dotenv
   HTTPX_MAX_CONNECTIONS=40
   HTTPX_MAX_KEEPALIVE_CONNECTIONS=20
   ```
2. **调大批量并发**: `BATCH_MAX_CONCURRENCY=20` (批量端点内部并发上限)。
3. **多 Key 分摊上游配额** (v1.5.0): `GOOGLE_API_KEYS="k1,k2,k3"` — 池按轮询选 Key, N 个 Key 真实吞吐约 N×上行。
4. **多 worker 提升本地并发**: `uvicorn main:app --workers N` (注意: 进程内缓存/限流不共享, 需 Redis 再上多副本)。
5. **网关层**: nginx `worker_processes auto` + `keepalive`, 生产关闭彩色日志 (`LOG_FORMAT=json`) 可降低单请求固定开销。

## 五、复现

```bash
# 启动 (默认连接池)
GOOGLE_API_KEYS=<real> API_MASTER_KEY=1 python -m uvicorn main:app --port 8092
python scripts/loadtest.py --url http://127.0.0.1:8092/v1/chat/completions --mode cache --levels 1,2,5,10,15,20,30,40 --per 30
python scripts/loadtest.py --url http://127.0.0.1:8092/v1/chat/completions --mode upstream --levels 1,2,5,10,15 --per 12

# 调参后
HTTPX_MAX_CONNECTIONS=40 HTTPX_MAX_KEEPALIVE_CONNECTIONS=20 python -m uvicorn main:app --port 8093
python scripts/loadtest.py --url http://127.0.0.1:8093/v1/chat/completions --mode upstream --levels 5,10,20,30 --per 10
```
