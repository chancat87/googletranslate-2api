## 一、结论 (TL;DR)

| 问题 | 答案 (真实实测) |
|---|---|
| 能不能并发调用? | **能**。并发 1→40 全部返回 200, 全程 0 错误、0 429 (cache 与 upstream 模式均验证) |
| 最高支持多少并发? | **正确性上限未测到** (conc=40 仍全 200); 性能拐点在 conc≈5-10 |
| 本地承载 (缓存命中) | 单 worker 吞吐 ~20-27 QPS, p50 36-810ms; 瓶颈是单 worker 事件循环 + 控制台日志固定开销 (~36ms/请求), **不是连接池** |

## 四、怎么高并发调用 (可操作)

1. **调大上游连接池** (v1.5.1 新增可配):
   ```dotenv
   HTTPX_MAX_CONNECTIONS=40
   HTTPX_MAX_KEEPALIVE_CONNECTIONS=20
   ```
2. **调大批量并发**: `BATCH_MAX_CONCURRENCY=20` (批量端点内部并发上限)。
3. **多 Key 分摊上游配额** (v1.5.0): `GOOGLE_API_KEYS="k1,k2,k3"` — 池按轮询选 Key, N 个 Key 真实吞吐约 N×上行。
4. **多 worker 提升本地并发**: `uvicorn main:app --workers N` (注意: 进程内缓存/限流不共享, 需 Redis 再上多副本)。
5. **网关层**: nginx `worker_processes auto` + `keepalive`, 生产关闭彩色日志 (`LOG_FORMAT=json`) 可降低单请求固定开销。

## 七、高并发调优实验 (2026-09-22 01:30, v1.5.3)

进一步压并发，验证"日志开销 / 单 worker 事件循环 / 多 worker"三个假设。环境: Windows 11 / i9-12900HX 16C24T / uvicorn。

### 结论

1. **单 worker 本地承载 (缓存命中) 约 15-35 QPS**, 高并发 (conc 100-200) 时服务端排队, p50 升到 1-3.5s, 是事件循环 + 每请求固定成本 (缓存/序列化/metrics/日志) 的上限, 不是上游配额。
2. **关闭 INFO 日志 (`LOG_FORMAT=json LOG_LEVEL=WARNING`)** 收益很小 (双客户端合计 29→32 QPS), 但显著降低日志写入/存储; 生产仍建议关。
3. **压测工具单进程有 ~15-20 QPS 上限**: 单个 `loadtest.py` 进程 + httpx 默认连接池 (100/keepalive 20) 打不满服务; 双进程并行才看到服务真实承载 (单 worker 约 29-32 QPS)。
4. **Windows 上 `--workers 4` 未提升吞吐** (合计仍 ~32 QPS): uvicorn 多 worker 共享监听 socket, Windows 无 SO_REUSEPORT, 连接 accept 分配不均匀, 长连接会粘到少数 worker。Linux 容器 + nginx upstream 轮询 (默认配置) 才会真正分摊负载。

### 数据

- 1 worker, text INFO, 1 进程, conc 40-200: 15.1-16.1 QPS, p50 1.1-1.5s, 0 错/0 429
- 1 worker, json INFO, 1 进程, conc 40-200: 14.4-18.9 QPS, p50 1.0-1.6s, 0 错/0 429
- 1 worker, json INFO, 2 进程, conc 100×2: ~28.7 QPS, p50 3.4-3.6s, 0 错/0 429
- 1 worker, json WARNING, 2 进程, conc 100×2: ~31.9 QPS, p50 2.9-3.0s, 0 错/0 429
- 4 worker, json INFO*, 1 进程, conc 40-200: 10.7-15.3 QPS, p50 1.4-2.7s, 0 错/0 429
- 4 worker, json WARNING*, 2 进程, conc 100×2: ~31.7 QPS, p50 3.5-3.9s, 0 错/0 429

\* 多 worker 时缓存为进程内, 预热用 `--warm-repeat <workers>` 保证每个 worker 都命中; 数据受 Windows accept 分配不均影响。

### 要真正提高并发, 需要做这些 (按收益排序)

1. **多上游 Key (`GOOGLE_API_KEYS="k1,k2,..."`)**: 真实翻译吞吐唯一线性扩展手段, N 个 Key ≈ N×10 QPS。文档已支持, 无需改码。
2. **Linux 容器 + nginx 做负载均衡**: nginx `upstream` 轮询多 worker/多副本 (已加 `keepalive 32`), Linux 无 Windows accept 分配问题, 缓存命中承载随 worker/副本线性涨。
3. **Docker 调参**: `APP_WORKERS≈CPU 核数`、`cpus` 抬到 2+、`HTTPX_MAX_CONNECTIONS=40`、`LOG_LEVEL=WARNING` (本版已支持)。
4. **共享缓存 (Redis)**: v1.6.0 已实现 — `CACHE_BACKEND=redis` + `REDIS_URL`, 多 worker/多副本共用一份翻译缓存, 提高缓存命中率, 减少打上游; 不可用时自动回退内存。
5. **网关限流**: 需要时开 `RATE_LIMIT_ENABLED=true` 或 nginx `limit_req`, 防单 Key 被打到 429。

## 八、极限压测 1000 并发 (2026-09-22 11:40, v2.13.6, 生产)

新增 `scripts/extreme_loadtest.py`: 显式调高 httpx `max_connections=1500`，单进程真正打出 1000 并发，避开默认 100 连接上限导致的结果失真。

### 缓存命中模式（Redis 共享缓存，不耗上游配额）

| conc | ok/总 | err | 429 | qps | wall | p50 | p95 | p99 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1000 | 1000/1000 | 0 | 0 | 32.2 | 31.1s | 18094ms | 29216ms | 30385ms |

### 真实上游模式（每请求唯一文本，直接打 Google）

| conc | ok/总 | err | 429 | qps | wall | p50 | p95 | p99 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1000 | 1000/1000 | 0 | 0 | 16.8 | 59.6s | 38340ms | 58273ms | 58915ms |

### 结论

1. **1000 并发全 200、0 错 0 429**：当前生产单机（1 vCPU / 1.7Gi）网关+蓝绿双副本+Redis 没有崩溃，也没触发 Google 上游限流。
2. **吞吐没有随并发线性上涨**：缓存命中 32.2 QPS、真实上游 16.8 QPS；p50 18-38s、p95 29-58s，说明瓶颈是单机事件循环/服务端排队，而不是并发不够。
3. **要达到真正的 1000 QPS**：需要多 Key（N×10 QPS 线性扩展）+ 多副本/多机横向扩展 + 付费住宅代理；单机 1 核 1.7G 的实测天花板就是 17-32 QPS。
